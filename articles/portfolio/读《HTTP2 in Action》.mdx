## HTTP的发展历史
http 的第一个规范 http0.9 在 1991 年发布，当时 http0.9 非常简单，请求方式都只有 get 一种。

随着万维网的迅速崛起，到 1995 年 http0.9 的局限性已经到了不可忽视，因此 http1.0 规范在 1996 年应运而生。

http1.0 规范在 1996 年发布，http1.0 规范中新增了 post、put、head(HEAD方法允许客户端获取资源的所有元信息（例如HTTP头）而无须下载资源本身,此方法大大节省流量) 等请求方式，并且新增了三位数的状态码，图片视频等其他类型文件的下载等。

9 个月之后在 1997 年 http1.1 发布，http1.1 对 http1.0 进行了优化，如支持管道、长连接、强制 Host 首部(由原来的相对地址变成了绝对地址， 因为现在一个web服务器上会托管多个网站，只有精准的地址才能访问到正确的资源)、缓存、cookie、代理、权限验证等。

## HTTP0.9
HTTP的第一个规范是1991年发布的0.9版本。规范文档只有不到700个单词。HTTP0.9 版本的协议非常简单，只包含了 GET 请求方法和一个 URL。

服务端使用HTML格式的消息进行响应。在处理错误时，规范声明：​“错误响应以可读的文本显示，使用HTML语法。除了文本的内容，没法办法区分错误响应和正确响应”。

## HTTP1.0
到1995年，HTTP/0.9这个简单协议的局限性已经不可忽视，大多数Web服务器都已经实现了远超0.9规范的扩展。

HTTP/1.0 版本的规范文档在0.9版本的基础上，增加了更多的请求方法，如 POST、HEAD、PUT 等。同时，规范还增加了更多的响应状态码，如 200、301、404 等。

GET和POST的一个重要区别是GET请求是幂等的，而POST请求不是。这意味着对于同一个URL的多个GET请求，应始终返回相同的结果，而POST请求则可能返回不同的结果。

## HTTP1.1
HTTP/1.1的首个规范发布于1997年1月。HTTP/1.1规范引入了许多新的特性，包括强制添加Host首部、持久连接、缓存、身份验证等。

### Host首部
在设计HTTP协议之初，一个Web服务器只能托管一个网站，所以URL的主机名部分是不言自明的，因为在发送HTTP请求之前，用户肯定已经连接到了主机。如今，很多Web服务器上面有多个网站（虚拟主机托管）​，所以告诉服务器要访问哪个网站和访问哪个相对URL同样重要。

Host作为必选项是HTTP/1.1的重要改进，这使得服务器能够充分利用虚拟主机托管技术，无须顾及因为新增网站而新加独立主机所带来的复杂性。

HTTP/1.1引入的HTTP代理允许通过中间HTTP服务器连接到目标HTTP服务器。代理的语法要求所有的请求使用完整的绝对URL，但实际的Web服务器（也称为源服务器）要求强制使用Host首部。

我们知道，使用Host首部对于避免破坏现有服务器是必要的，但它强制要求HTTP/1.1客户端和服务器使用虚拟主机式请求，只有这样才能完全兼容HTTP/1.1实现。有人认为，在HTTP的未来某个版本中，这种情况会得到更好的解决。

HTTP/1.1规范声明，​“为了支持在某些未来版本的HTTP中，转为使用绝对URL形式，服务器必须接受请求中的绝对URL形式，即使HTTP/1.1客户端只会在使用代理的请求中发送它们。​”但是，HTTP/2并未彻底解决此问题，而是使用:authority伪首部字段替换Host首部


### 持久连接（KEEP-ALIVE）
HTTP中的另外一个被很多HTTP/1.0服务器所支持的重大更新是持久连接，但是它没被包含在HTTP/1.0的规范中。起初，HTTP仅仅是一个请求-响应协议。客户端打开连接，请求资源，获得响应，然后断开连接。随着互联网的媒体内容变得更加丰富，关闭连接被证明是一种浪费性能的行为。

显示一个页面需要多个资源，所以关闭连接之后还要重新打开它，这导致了不必要的延迟。这个问题被一个新的Connection首部解决了，这个HTTP首部可以随着HTTP/1.0的请求被发送。通过指定此首部值为Keey-Alive，客户端可以要求服务器保持连接打开，以支持发送更多的请求。

服务器像往常一样响应，但如果它支持持久连接，它会在响应中包含一个Connection: Keep-Alive首部：这个响应告诉客户端，在发送完响应之后，马上就可以在同一个连接上发送一个新的请求，所以服务器不用每次都关闭再重新打开连接。

当使用持久连接时，想要知道响应何时完成可能会更困难。对于非持久连接，关闭连接是一个表明服务器已经完成了发送的好信号！所以，必须使用Content-Length首部来定义消息响应体的长度，以便当整个消息体传输完成后，客户端可以发送一个新请求。

### 缓存

http的缓存主要可以分为两种，强缓存和协商缓存。
#### 强缓存

针对强缓存，http1.0利用expires字段来标记资源一个具体的日期时间, 如果在这个截至日期之前需要这个资源，则直接从缓存里取。

expires的缺点显而易见，因为是一个具体的日期值，我们知道服务器和客户端是极有可能出现时间偏差的，并且客户端和服务端可能还跨时区，另外客户端时间也是可以被修改的，这都会造成客户端和服务端时间不同步。

针对expires的问题，http1.1提出了cache-control:max-age这个属性, max-age值是一串数字，单位是秒，表示这个资源在多少秒内是缓存有效的。

#### 协商缓存
针对协商缓存，http1.0利用last-modified来标记资源最近的修改时间，客户端再次请求该资源的时候会在请求头中把last-modified的值带在if-modified-since字段值中，有服务端来判断，如果目前资源的修改时间和请求头中携带的if-modified-since的值一致，则返回304，否则返回200。

这种协商缓存也有一些缺点，比如我们有时候虽然动了文件但是并没有改变内容，这种情况我们其实是希望能使用缓存的，还有一个问题是last-modified的时间只能精确到秒，如果资源在秒级有改变，是无法识别出文件发生更新的。

针对这些问题http1.1引入了etag，etag是服务器端生成的一串数字，优点类似于文件指纹。客户端请求时会把etag的值带在If-None-Match中，由服务端判断两者是否一致，一致则表示缓存可用。

etag这种方式虽然更能精确的标记资源是否更新，但是这种方式也有弊端，就是比较消耗性能，因为你如果要绝对的准确你需要要根据资源内容来生成tag。etag分为强认证和弱认证，强认证会校验资源全部内容，弱认证只校验资源的一部分。

## HTTP1.1的缺陷

随着宽带和光纤等技术的以及互联网的发展，我们从简单的静态网站转变为交互式的网页，对网络传输速度的要求也越来越高。HTTP1.1渐渐无法满足人们的需求。

HTTP1.1的根本问题是性能问题。而导致HTTP1.1性能问题的主要原因又是多个方面的，比如队头阻塞和慢启动等等

HTTP1.1的性能问题主要体现在两个方面：

### 队头阻塞
在 TCP 协议中，每个数据包都有唯一的序号。但如果多个包中某个序号比较靠前的在传输过程中发生了丢包，其它序号靠后的包即使已顺利到达，也需要在接收方的缓冲区中等待，直到队头包重传成功才能将报文组装并返回给应用层。这个现象称为队头阻塞。

### 慢启动
TCP 协议中，为了避免拥塞，发送方需要控制发送速度。TCP 协议中规定，当发送方发送一个报文时，发送方会根据当前网络拥塞程度，决定发送报文的大小。这个过程称为慢启动。

## 针对HTTP1.1的优化方案
针对HTTP1.1的优化方案都可以归结为下两类：1.使用多个HTTP连接。2.合并HTTP请求。

### 使用多个HTTP连接。
大多数浏览器可以为每个域名打开6个连接。一般通过域名分片的手段来突破这个限制。

例如将静态资源比如将css文件、js文件、图片等资源放置在其他域名下，来增加连接数。

除了提高并发数，域名分片还有其他优势，比如减小HTTP请求首部（如将不需要cookie的资源放在一个域名下）​​。通常，这些域名托管在同一台服务器上。共享相同的资源但使用不同的域名会让浏览器误以为服务器是相互独立的。

使用多个HTTP连接听起来不错，但它也有缺点。当开启多个HTTP连接时，客户端和服务器都有额外的开销：打开TCP连接需要时间，维护连接需要更多的内存和CPU资源。

开启多个 HTTP 连接还有一个问题就是没有充分利用 TCP 连接的优势，tcp 是一种可靠的协议，如果包丢失会触发重发机制，所以在连接初期，tcp 会控制包的数据量，以确定网络是否拥堵，随着时间的增加，并确保网络通常的情况下会处理更大的数据量，TCP 拥塞窗口的大小受 TCP 慢启动算法控制。（TCP 慢启动算法会逐渐增加拥塞窗口的大小，直到网络拥堵，拥塞窗口大小会减小，直到网络再次变得拥堵，拥塞窗口大小会再次增加），所以，在 CWND 比较小时，可能需要多个 TCP ACK 消息才能发出一个完整的 HTTP 请求。

还有一个问题由于 tcp 没有优先级概念，更容易造成阻塞。这也说明了为什么浏览器限制每个域名开启的连接数为 6。尽管可以增大这个数字（一些浏览器允许这么做），但考虑到每个连接的额外开销，收益会比较低。

### 合并HTTP请求
另外一个常见的优化技术是发送更少的请求，包括：减少不必要的请求（比如在浏览器中缓存静态资源）​，以更少的HTTP请求获取同样的资源。后续会详细介绍这种优化方式。

##   HTTP2
由于 http1.1 的各种问题，谷歌在 2009 年提出了 SPDY 协议，SPDY 协议在 http1.1 的基础上做了一些改进，比如：多路复用、请求优先级、头部压缩等等。

spdy 被多年使用证明了可靠性之后，在 2014 年，基于 spdy 协议的 http2.0 协议被提出。

http2.0 的主要改进点：

### 二进制分帧
HTTP/1和HTTP/2的主要区别之一是，HTTP/2是一个二进制的、基于数据包的协议，而HTTP/1是完全基于文本的。

基于文本的协议方便人类阅读，但是机器解析起来比较困难。在早期，HTTP只是作为一个简单的请求-响应协议，这在当时还可以被人接受，但对于现代的互联网来说，它带来的限制越来越明显。使用基于文本的协议，要先发完请求，并接收完响应之后，才能开始下一个请求。

虽然HTTP/1.1引入了管道化和分块编码。分块编码允许先发送消息体的一部分，当其余的部分可用时再接着发。这时HTTP消息体被分成多个块，客户端可以在完整收到所有数据之前就开始处理这些分块的内容（服务端也可以收到分块请求）​。

这个技术常用于数据长度动态生成的场景，预先不知道总数据长度。分块编码和管道化都有队头阻塞（HOL）的问题——在队列首部的消息会阻塞后面消息的发送，更不用说，管道化在实际应用中并没有得到很好的支持。

HTTP/2中的二进制表示用于发送和接收消息数据，但是消息本身和之前的HTTP/1消息类似。二进制帧通常由下层客户端（Web浏览器或Web服务器）或者类库来处理。我们之前提到过，像JavaScript这样的上层应用不需要关注消息是如何被发送的，大多数时候可以对HTTP/2连接和HTTP/1连接一视同仁。


### 多路复用
HTTP/1是一种同步的、独占的请求-响应协议。客户端发送HTTP/1消息，然后服务器返回HTTP/1响应。

这种方式在现代互联网中是可行的，因为大多数应用都是基于请求-响应的。但是，在某些情况下，这种方式会导致性能问题。

比如，在一个页面中，有多个图片需要加载，每个图片的加载时间可能不同。如果使用HTTP/1，每个图片的加载都需要等待前一个图片加载完成后才能开始。这会导致页面加载时间非常长，用户体验非常差。

HTTP/2允许在单个连接上同时执行多个请求，每个HTTP请求或响应使用不同的流。通过使用二进制分帧层，给每个帧分配一个流标识符，以支持同时发出多个独立请求。当接收到该流的所有帧时，接收方可以将帧组合成完整消息。

帧是同时发送多个消息的关键。每个帧都有标签表明它属于哪个消息（流）​，这样在一个连接上就可以同时有两个、三个甚至上百个消息。不像在HTTP/1中，大多数浏览器只能并发6个请求。

### 请求优先级

在HTTP/2之前，HTTP是单独的请求-响应协议，因此没有在协议中进行优先级排序的必要。客户端（通常是Web浏览器）在HTTP之外就决定了请求的优先级，因为同时只能发送有限数量（通常为6个）的HTTP/1请求。

这种优先级通常需要先请求关键资源（HTML、影响渲染的CSS和JavaScript）​，然后再请求非阻塞的内容（如图像和异步JavaScript）​。请求会进入队列，等待可用的HTTP/1连接，而队列的优先级由浏览器管理。

现在HTTP/2对并发的请求数量的限制放宽了很多（在许多实现中，默认情况下允许同时存在100个活跃的流）​，因此许多请求不再需要浏览器来排队，可以立即发送它们。这可能导致带宽浪费在较低优先级的资源（例如图像）上，从而导致在HTTP/2下页面的加载速度变慢。

所以需要控制流的优先级，使用更高的优先级发送最关键的资源。流的优先级控制是通过这种方式实现的：当数据帧在排队时，服务器会给高优先级的请求发送更多的帧。流优先级的控制力比HTTP/1强大，在HTTP/1中，不同的连接是互相独立的，没有优先级关系。

在HTTP/1中，无法指定一些连接的优先级。如果你有5个关键资源，和1个非关键资源，则在HTTP/1下，所有资源都可以在6个独立的连接上以相同的优先级请求，要不然只能先发送前5个资源，第6个资源暂时不发出去。在HTTP/2下，所有5个请求都可以用适当的优先级发送，使用优先级决定给每个响应分配多少资源。

流量控制是在同一个连接上使用多个流的另一种方式。如果接收方处理消息的速度慢于发送方，就会存在积压，需要将数据放入缓冲区。而当缓冲区满时会导致丢包，需要重新发送。在连接层，TCP支持限流，但HTTP/2要在流的层面实现流量控制。以视频网页为例。如果用户暂停视频，可以仅暂停视频流，允许加载网站的其他资源，这是更好的选择。

### 首部压缩
HTTP首部（包括请求首部和响应首部）用于发送与请求和响应相关的额外信息。在这些首部中，有很多信息是重复的，多个资源使用的首部经常相同。比如，Host、Accept-Encoding、User-Agent、Accept-Language等。它们会随着每个请求被发送，通常和之前的请求使用相同的值。

另外响应首部也可能会有重复，会很浪费资源。有些特殊的响应首部，如CSP（Content Security Policy）首部，可能会很大，也可能会有重复。这对于小的请求来说特别糟糕，在这种情况下，HTTP首部将占下载资源的很大一部分。

HTTP/1允许压缩HTTP正文内容（Accept-Encoding首部）​，但是不会压缩HTTP首部。HTTP/2引入了首部压缩的概念，但是它使用了和正文压缩不同的技术。该技术支持跨请求压缩首部，这可以避免正文压缩所使用算法的安全问题。

### 服务器推送
HTTP/2引入了服务器推送的概念，允许服务器在客户端请求之前发送资源。但是目前位置由于服务端推送的实际效果和性能问题，从 Chrome 85 开始，谷歌默认禁用服务器推送。

### HTTP 的缺点

1. 通信使用明文不加密，内容泄露被窃听
2. 不验证通信方身份，被伪装
3. 无法证明报文完整性，被篡改

## HTTPS与HTTP的区别
HTTP + 通信加密(SSL) + 身份认证 + 完整性保护 = HTTPS

1. 加密通信线路
通过和 SSL（Secure Socket Layer，安全套接层）或 TLS（Transport Layer Security，安全层传输协议）的组合使用，加密 HTTP 的通信内容
2. 身份认证
  通过查明对手的证书认证服务器不是伪装的
3. 完整性校验
  消息在传输过程中未被更改，因为整个加密消息已经过数字签名，并且该签名在解密之前已通过加密验证
但是增加一系列的功能的代价是需要使用更多的内存、流量、和 cpu 资源以及需要付费购买买证书

## SSL与TLS的区别
SSL是TLS的前身。
  
SSL是由Netscape发明的。Netscape没有对外发布SSLv1,在第一个生产版本是1995年发布的SSLv2。1996年发布了SSLv3。由于SSL由Netscape拥有，因此它不是正式的互联网标准，后来SSL被标准化为TLS（传输层加密）。

TLSv1.3在2018年被批准为标准。但它更安全，更高效。尽管有这些标准化的、更新、更安全的版本可用，许多人还是认为SSLv3已经足够了，所以在很长一段时间内它是事实上的标准，虽然许多客户端已经支持TLSv1.0了。

然而，在2014年，在SSLv3中发现了重大漏洞，SSLv3因此被要求停止使用，并且浏览器也停止对它的支持。从这时人们才开始大量向TLS迁移。在TLSv1.0中发现类似的漏洞后，安全专家强烈建议使用TLSv1.1或更高版本。由于这段历史所造成的影响，人们对这些缩写的用法并不统一。许多人仍然将加密称为SSL，因为它在那么长的一段时间里都是标准。
